RK3528A · ARMv8 Crypto Extensions · Mihomo / Nikki

Mihomo 会不会用到
RK3528A 的加密指令加速？

会，但需要说清楚调用路径：Mihomo 不调用 Rockchip 独立 Crypto Engine，也不借道 Linux 内核 Crypto API；它由 Go 用户态密码库检测 CPU 能力，并在 AES-GCM 会话中直接执行 ARMv8 AES / PMULL 指令。

现场快照 · ssh e20c · 2026-08-03 · ImmortalWrt 25.12.1
最终结论
ARMv8 AES / PMULL 已启用，Mihomo 可自动使用

TLS / QUIC 最终协商为 AES-GCM 时，Go 直接进入 ARM64 汇编加速路径。

不是这条路径
Rockchip Crypto Engine

当前固件未发现独立 Crypto Engine 的驱动、设备树节点或平台设备。

重要边界
不是每条连接都用 AES

若协商为 ChaCha20-Poly1305，便不会执行 AES / PMULL 指令。

从 Nikki 到 ARMv8 指令的调用链

Control plane → data plane → CPU

Nikki 位于控制面，负责配置、启动和透明代理规则；真正逐包处理、协议封装和加解密的是 Mihomo。

1

LuCI / UCI · Nikki

保存配置、生成运行目录、维护 nftables/TUN/TPROXY，并由 procd 拉起 Mihomo。Nikki 本身不加解密代理载荷。

→
2

Mihomo 入站与规则引擎

接收透明代理流量，完成 DNS、嗅探、规则匹配与代理组选择，决定 DIRECT 或具体出站节点。

→
3

协议出站适配器

当前节点类型为 AnyTLS、Hysteria2、Trojan、VLESS；建立 TLS / Reality / QUIC 等加密传输。

4

Go TLS / QUIC 密码栈

crypto/tls、uTLS 或 QUIC 调用 Go 的 AES-GCM / ChaCha20-Poly1305 等密码原语；最终算法由协议配置和握手协商决定。

→
5

Go CPU 能力分派

ARM64HasAES 与 ARM64HasPMULL 同时为真时，supportsAESGCM 成立，选择 Armv8.0 汇编实现。

→
6

RK3528A CPU 执行

AES 轮函数由 AESE/AESMC 等指令执行，GCM 认证乘法由 PMULL 加速；数据不需要送到独立外设。

AES-128/256-GCM

使用 AES + PMULL，明确进入 ARMv8 加速路径。

ChaCha20-Poly1305

不使用 AES / PMULL；走 ARM64/ASIMD 优化或对应实现。

DIRECT

没有 Mihomo 代理协议层加密；客户端自身 HTTPS 仍由客户端处理。

容易混淆：内核里的 gcm-aes-ce 和 Mihomo 里的 Go ARM64 AES-GCM 都能执行同一类 CPU 指令，但属于两套独立软件调用路径。Mihomo 通常不会通过 AF_ALG 调用 /proc/crypto 中的内核实现。

证据等级与不能过度推断的地方

Evidence boundary

已经确认

  • RK3528A 四核均向用户态暴露 AES 与 PMULL。
  • Go ARM64 AES-GCM 的硬件分派条件在本机成立。
  • Mihomo 为 ARM64 Go 原生构建，且未禁用 CPU AES。
  • 当前节点池全部为 TLS / QUIC 类代理协议。

不能仅凭现有 API 确认

  • Mihomo 控制 API 不公开每条 TLS/QUIC 连接最终协商的 cipher suite。
  • /proc/crypto 的 refcnt 不是算法调用次数，不能拿它证明 Mihomo 正在用。
  • 不能把 73 条活动连接全部表述为 AES-GCM；其中可能存在 ChaCha20-Poly1305。
  • 要逐连接硬证据，需要握手追踪、服务端日志或对照性能剖析。
